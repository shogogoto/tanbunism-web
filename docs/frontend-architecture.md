# フロントエンドの責務分担

見た目が似ているだけの画面を一つにまとめるのではなく、変更理由が同じ処理を共有する。
UIの基本部品とTailwindの配置は[UI部品ガイド](ui-components.md)を参照。

## 通信

`shared/lib/requestJson.ts`はJSONの取得・HTTPエラーの整形・ステータス保持を担当する。
接続エラーは既存の`networkFetch`、FastAPIのエラー本文は`apiErrorMessage`を利用する。
APIのベースURLもここから参照できる。

- キャッシュ更新、ドメイン型への変換、画面通知はfeature側に残す。
- 書き込みを自動再試行しない。中止されたリクエストのAbortErrorも変換しない。
- FormDataにJSON用ヘッダーを付けない。必要なヘッダーやsignalは呼び出し側が渡す。
- `204`は本文なしとして扱う。不正なJSONは成功扱いにせず、HTMLエラー本文を表示しない。
- `QuizApiError`のような固有エラー型は`createError`で維持できる。
- `shared/generated`や`features/quiz/generated`は直接編集しない。
  バイナリ取得や本文なしの専用APIまで無理にJSON通信へ統合しない。

## 学習計画

- `StudyPlanManager`: 選択・操作・ダイアログと更新操作の調整。
- `useStudyPlanData`: SWRによる取得、準備状況のポーリング、通知による再取得。
- `studyPlanView`: 検索・安定ソート・達成度計算。Reactやネットワークなしでテストする。
- `StudyPlanList`: PCの表とスマホのカード表示。取得や保存はしない。

一時的な選択や編集中の入力を、サーバー取得データのキャッシュへ混ぜない。
リソースIDの正規化やソートの欠損値の扱いは純粋関数側に集める。

## クイズの進行

- `QuizSession`: 問題・結果の表示、キーボード操作、フォーカス、復習進捗の公開。
- `useQuizSession`: 学習計画と推薦の取得、回答送信、おまかせ開始、再取得。
- `quizSessionState`: 選択・送信中・部分成功・誤答の再挑戦を扱う純粋なreducerと進捗計算。

推薦を段階的に受け取っても既存の選択肢順序は維持する。
計画変更・推薦再取得・unmountで古い処理を無効化し、別セッションの結果を混ぜない。
回答は二重送信を防ぎ、部分失敗時は未送信分だけを再実行する。
書き込み自体は中止できたと仮定せず、旧セッションの送信成功も学習進捗の再取得に反映する。

## 冒険状態の同期

`useAdventureState`はサーバーの冒険スナップショットとrevision、初回読み込み、
focus時の再取得、既存戦闘の復旧、旧ローカルセーブの提示、保存を担当する。
利用側の`GamePlay`はユーザーIDでkey付けし、ユーザー変更時に私有状態を作り直す。

- サーバーから受けた状態は`applyState`経由で反映する。
- `setSave`は取得済みダンジョン内容のローカルマージ用。進行状況の永続化には使わない。
- 保存中・移動中・回答送信中・戦闘中にはfocusによる読み直しを開始しない。
- 古い読み込みが後から届いても、新しい操作結果を上書きしない。
- 保存失敗時は最新状態を読み直すが、書き込みは再送しない。読み直しも失敗した場合でも元の保存エラーを保持する。

`useExplorationActions`は回復・入口施設の利用・宝箱を開く操作を担当する。
可否の純粋なルールは既存の`recoverAtEntrance`・`visitEntranceFacility`を再利用する。
操作中のロック・busy・エラー処理はhook内の非公開処理で共有するが、アプリ全体用の汎用コマンド基盤にはしない。
宝箱の通信失敗時には状態を再取得し、報酬の獲得要求を自動再送しない。
施設利用は保存成功時だけ`true`を返し、どの施設のパネルを開くかは`GamePlay`で決める。

探索・ダンジョン切り替え・ボス挑戦などのコマンド、ダンジョンデータ取得と画面配置は、
現時点では`GamePlay`側に残る。必要な機能変更に合わせ、スナップショット同期と別の責務として段階的に整理する。

## adminの編集

`useGameCatalogDraft`はローカルの未保存データ、読み込み、保存中、成功・失敗を管理する。
二重保存を抑止し、別の編集対象へ切り替わった後の古い応答は反映しない。
画面固有の削除可否、参照チェック、保存前の変更は呼び出し側に置く。
`normalize`にはモジュールレベルの関数か`useCallback`で安定した関数を渡す。
編集対象を変更して草稿を破棄する場合は、その対象をcallbackの依存に含める。

効果テンプレートの入力正規化・上書き判定は`templateDraft`へ置き、表の表示から分離する。
報酬のように別の保存単位を持つ画面を、同じ草稿hookへ無理に寄せない。

## 時計とグラフ

`useClock`は一定間隔で現在時刻を更新するだけのhook。
回答時の残り時間の固定、ダイアログを閉じても進行するルール、タイムアウト送信は各戦闘側の責務。

グラフの`pathsToEnd`は明示的なスタックと現在の経路上の集合を使う。
循環を終端とはみなさず、実際の終端まで達する経路だけを返す。
全体の訪問済み集合で枝を省略すると合流する別経路が失われるため、そうしない。

## 検証の範囲

純粋関数と共通hookを単体テストし、既存画面の操作・保存テストも維持する。
横断的な変更では最後にVitest全体・型チェック・lint・本番ビルドを確認する。
認証・権限の安全性は、部品共通化やテスト成功だけでは保証されない。別途API側も含めて検証する。
